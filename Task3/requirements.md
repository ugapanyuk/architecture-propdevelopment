
# Требования к внешним интеграциям

| Категория | № | Требование | Обоснование |
| :--- | :-: | :--- | :--- |
| **Безопасность** | 1 | **HTTPS/TLS.** Все взаимодействия между системами PropDevelopment и платформой партнера должны осуществляться исключительно по зашифрованному каналу (HTTPS с использованием актуальной версии протокола TLS). | Защита от перехвата и изменения данных при передаче. |
| | 2 | **API Gateway как единая точка входа.** Все запросы к API партнера должны проходить через внутренний API Gateway PropDevelopment. Прямое обращение из `tenant-core-app` к партнеру запрещено. | Устраняет текущую проблему неконтролируемых интеграций. Позволяет централизованно управлять безопасностью, мониторингом, квотами и аутентификацией. |
| | 3 | **Защита от атак.** API партнера должно иметь встроенные механизмы защиты от распространенных атак (OWASP API Security Top 10), включая защиту от инъекций, DDoS и т.д. | Снижает риск компрометации как партнерской системы, так и системы PropDevelopment через уязвимости в API. |
| | 4 | **Аудит и логирование.** Все запросы к API, как успешные, так и неудачные, должны подробно логироваться на стороне API Gateway и на стороне партнера. Логи должны содержать идентификатор пользователя, тип операции, временную метку и IP-адрес. | Необходимо для расследования инцидентов, анализа активности и выявления аномалий. |
| | 5 | **Обработка чувствительных данных.** Биометрические данные (фото для распознавания лиц) и номера автомобилей должны обрабатываться в соответствии с законодательством РФ (ФЗ-152 "О персональных данных"). Партнер должен предоставить подтверждение соответствия и описать меры по защите этих данных. | Работа с биометрией требует высочайшего уровня защиты и строгого соблюдения правовых норм, чтобы избежать штрафов и репутационного ущерба. |
| **Аутентификация и Авторизация** | 6 | **Протокол OAuth 2.0.** Для аутентификации системы PropDevelopment (в лице API Gateway) в системе партнера должен использоваться протокол OAuth 2.0, поток `Client Credentials`. | Это стандартный и безопасный способ межсерверной аутентификации. Он позволяет не хранить статические ключи API в коде, а использовать временные токены доступа (access token). |
| | 7 | **Передача контекста пользователя (JWT).** Для авторизации действий конкретного пользователя (например, "открыть шлагбаум для собственника Иванова") система PropDevelopment должна передавать партнеру информацию о пользователе в виде подписанного JWT-токена. Партнер должен валидировать подпись этого токена. | Это предотвращает ситуацию, когда один пользователь может выполнить действие от имени другого. Партнер доверяет данным о пользователе, только если они подписаны доверенным ключом PropDevelopment. |
| | 8 | **Принцип минимальных привилегий.** API-ключи и токены доступа, выдаваемые партнером, должны иметь минимально необходимый набор прав для выполнения только заявленных функций (управление домофоном и шлагбаумом). | Снижает ущерб в случае компрометации токена. Например, токен не должен давать доступ к данным других клиентов партнера. |
| **Взаимодействие систем** | 9 | **Синхронное взаимодействие (Request/Response).** Для командных операций (открыть дверь/шлагбаум, получить список устройств) используется синхронная модель. Запросы инициируются системой PropDevelopment. | Стандартная модель для операций, требующих немедленного ответа. |
| | 10 | **Асинхронное взаимодействие (Webhooks).** Для уведомлений о событиях (кто-то вошел, попытка доступа) партнерская платформа должна использовать механизм Webhooks, отправляя POST-запросы на специальный endpoint в API Gateway PropDevelopment. | Это эффективный способ получения событий в реальном времени без необходимости постоянно "опрашивать" API партнера (polling), что снижает нагрузку на обе системы. |
| | 11 | **Контракт API (OpenAPI/Swagger).** Партнер обязан предоставить подробную и актуальную спецификацию своего API в формате OpenAPI 3.0 (Swagger). | Ускоряет и упрощает разработку, позволяет автоматически генерировать клиентский код и проводить тестирование. Снижает риск ошибок из-за несоответствия документации и реальной работы API. |
| | 12 | **Отказоустойчивость.** Взаимодействие должно предусматривать механизмы обработки сбоев: повторные запросы (retry) с экспоненциальной задержкой, таймауты, а также четкие коды ошибок для разных сценариев (недоступность сервиса, неверные данные, отсутствие прав). | Обеспечивает стабильность работы сервиса для конечного пользователя даже при кратковременных сбоях на стороне партнера или в сети. |
